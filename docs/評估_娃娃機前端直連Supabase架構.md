# 娃娃機專案「前端直連 Supabase + RLS」架構評估

> 2026-08-28 建立。緣起：咖哩問「把天鷹後端帳密表也搬 SQL，其他讀 Sheet 的是不是也可以跟著搬」，
> 過程中查證娃娃機專案（`sky03104/wei`）主分支只是加了 `CacheService` 快取（跟搬 SQL 無關），
> 真正的 SQL 遷移在未合併的分支 `feature/supabase-migration`。本文評估這個分支的做法能不能、
> 該不該搬進天鷹保全 APP。**純評估文件，不是執行中的遷移規劃**（跟 `docs/SQL遷移規劃_*.md`
> 那幾份不同，那幾份是「已拍板要做」，這份是「要不要做」）。

## 一、娃娃機那個分支實際做了什麼

**動機（跟天鷹已驗證的判斷標準完全吻合）**：原架構 `dbReadAll()`（`apps-script/Db.gs`）
每次都整張分頁讀進記憶體再用 JS 篩選，效能跟著「分頁累計筆數」變慢，不是跟著「查詢區間
大小」變慢——原本靠「季度封存」硬撐（把上一季以前的紀錄搬到獨立分頁）。换成 Postgres
+ 索引之後這個問題直接消失，季度封存機制整個拿掉。這跟天鷹 TODO-36/37/39/40 判斷「該不該
搬 SQL」用的同一條規則（會不會無上限持續累積）互相印證。

**但架構走的方向跟天鷹目前做法完全不同**：

| | 天鷹目前做法（TODO-36/37/39/40） | 娃娃機 `feature/supabase-migration` |
|---|---|---|
| API 入口 | 前端照樣打 GAS，GAS 內部改讀/寫 Supabase | 前端直連 Supabase client，GAS 幾乎被繞過 |
| 業務邏輯位置 | 留在 GAS（`.gs` 檔案裡的 JS 函式） | 搬成 Postgres function（`rpc()`），SQL/plpgsql 寫邏輯 |
| 權限判斷 | GAS 裡的 `if/else`（`checkPermission`、`ACTION_ROLES`） | Postgres Row Level Security（RLS）policy，資料庫層面擋 |
| 登入/Session | 沿用既有機制（token、Sessions 表） | 整套換成 Supabase Auth（JWT），舊密碼機制作廢 |
| 例外情況 | 無 | 「建帳號/改密碼」仍需 service role key，用 Edge Function 補一小塊後端 |

娃娃機這條路線分 6 個 Phase：Schema 設計 → Auth/RLS 拍板 → 業務邏輯搬 rpc → 資料遷移腳本
→ 雙軌驗證（`BACKEND` 開關切換 GAS/Supabase，兩邊並存同一份 `app.js`）→ 正式切換。
**目前卡在 Phase 5 完成、Phase 6（正式切換）還沒開始**，也就是說：

- 沒有正式環境的量化效能對比數字（不像天鷹自己那幾個 TODO 都有「Xms → Yms」的實測）
- 只在瀏覽器裡用真的 Supabase 專案手動點過一輪功能，確認「跑得動」，不是長期正式運作驗證
- 遷移完的帳號密碼全部要求使用者登入後手動改密碼（原密碼機制的 salt+pepper 沒辦法帶過去）

## 二、對天鷹的可行性評估

### 2.1 效能面：天鷹用不到這個等級的手術

娃娃機要走「前端直連＋RLS」，根本原因是 GAS 本身的**執行時間配額**與**冷啟動開銷**在它的
使用場景（多人同時操作、高頻背景輪詢）撐不住，連 CacheService 都只能緩解不能解決。天鷹
目前的效能債（打烊/開店/施工單/物流/班表歷史）都已經用「GAS 內部改讀 Supabase，前端不變」
這種侵入性小很多的方式解決掉了，實測效能提升都在 3~7 倍（1396ms→431ms、3010ms→847ms 等），
沒有證據顯示這樣不夠、需要再往「繞過 GAS」這個方向升級。

### 2.2 安全面：RLS 對天鷹是全新的攻擊面，不是既有機制的搬遷

天鷹的員工個資（生理假紀錄、緊急聯絡清單、帳密）目前靠三層把關：`DEFAULT_PERMS` → 前端
`checkPermission()` → **GAS 每個 action 驗 token+角色**，最後一層在伺服器端、使用者拿不到。
若改成前端直連 Supabase + RLS，等於要把「誰能看什麼」的規則**逐條翻譯成 Postgres policy**，
翻譯出錯的後果是資料庫層面直接外洩（不像 GAS 邏輯錯了頂多回傳錯誤訊息，RLS policy 寫錯可能
是「整張表都查得到」）。娃娃機那邊機台資料外洩頂多是營業數字被看到，天鷹是員工個資，
風險量級不同，翻譯這批 policy 需要的驗證強度也該更高——娃娃機那邊光是 RLS 邊界就用
`authenticated`/`anon`/多角色分別測過一輪，天鷹要做只會更費工。

### 2.3 帳密表本身：不適合當這個架構的敲門磚

回到咖哩最初的問題——帳密表拿去當「前端直連＋RLS」的試點看似合理（反正遲早要搬），但實際上
帳密/Session 正是娃娃機那條路線裡**最特殊、最不能直接套用**的一塊：整套換成 Supabase Auth
會讓天鷹現有的登入機制（`login`/`verifySession`/`changePassword`，2026-07-26 剛做完後端驗證）
整個報廢，且强制全體員工改密碼。如果只是想解決帳密表的效能問題，它本來就固定 48 筆、
不是瓶頸（見前次對話結論），沒有理由為了它去換整套 Auth 機制。

### 2.4 工程量對比

天鷹目前一個 TODO（例如 TODO-40 物流車輛）的搬遷是：建一張表、GAS 改幾支函式、寫遷移腳本、
比對筆數、上線。娃娃機這條分支是：設計整套 schema、拍板 RLS 權限模型、把**所有**業務邏輯
逐支重寫成 Postgres function、前端整層改寫、Auth 整套換掉、Edge Function 補特殊案例——
規模是「單表遷移」的數十倍，且天鷹的工具數量（十幾支 `tool_*.html` 各自獨立 GAS）遠多於
娃娃機（單一系統），要做就不是一次能做完的事。

## 三、結論與建議

**不建議天鷹比照娃娃機走「前端直連 Supabase + RLS」這條路線。** 理由：
1. 天鷹目前沒有娃娃機那種「GAS 配額撐不住」的症狀，現有漸進式做法（GAS 內部換讀寫、前端不變）
   已經把該解決的效能債都解決了，且工程風險小很多
2. 天鷹的個資敏感度比娃娃機的營業數字高，RLS 翻譯錯誤的代價更大，沒有急迫理由現在承擔這個風險
3. 帳密表不是效能瓶頸，沒必要為了它去換整套 Auth 機制

**值得繼續觀察、但不用現在跟進的**：等娃娃機那條分支真的走完 Phase 6、正式切換運作一段時間
（1~2 週穩定觀察期）、拿到正式環境的量化數據之後，如果數字證明「前端直連＋RLS」在維護成本
上真的比「GAS 當閘門」輕鬆很多，再回頭評估要不要挑天鷹裡**最單純、風險最低**的單一工具
（例如筆數小、非個資類的獨立 GAS 專案）當試點，不要一開始就拿帳密表下手。

**現階段維持現有方向**：天鷹已拍板的 TODO-36/37/39/40 模式（GAS 當 API 層/閘門，內部資料源
從 Sheets 換 Supabase）continue，帳密表維持 Sheets（固定筆數、非效能瓶頸），不動它。
