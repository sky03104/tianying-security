### 📅 2026-08-27：GAS的UrlFetchApp對大寫PATCH/DELETE會靜默忽略，不報錯但沒真的執行
- 症狀：施工單管理的報到換證同步Supabase，HTTP回應204（成功），但資料庫的欄位完全沒有變化，一路排查了快一小時
- 根因：GAS的`UrlFetchApp.fetch(url,{method:...})`，`method`參數用大寫`'PATCH'`或`'DELETE'`會被靜默忽略（不報錯，可能被當成別的方法處理），只有小寫`'patch'`/`'delete'`才會真正執行。已確認`'GET'`/`'POST'`大寫沒有這個問題，官方文件混用大小寫寫法容易讓人誤以為都可以
- 修法：所有GAS呼叫外部REST API的PATCH/DELETE一律改小寫。回頭檢查發現**同一個bug在已上線的班表管理專案也存在**（換月時「標記舊版本為superseded」用的也是大寫PATCH，代表可能已經悄悄失效一段時間沒被發現），一併修復
- 一行規則：**GAS的UrlFetchApp呼叫外部API時，PATCH/DELETE一律寫小寫**；驗證這類寫入功能時**不能只看HTTP狀態碼**，204/200不代表真的執行到，一定要另外查一次資料庫確認資料真的變了

### 📅 2026-08-27：Supabase/PostgREST單次GET請求預設上限1000筆，不分頁會悄悄漏資料
- 症狀：施工單管理的每日備份腳本，第一次執行log顯示「施工單1000筆」，但資料庫實際有4302筆，備份漏了三千多筆，完全沒有錯誤訊息。同一天稍晚，打烊/開店/物流車輛統計的核對筆數、月統計等功能也各自踩到同一個坑（物流的月統計甚至因此把8月14日之後的資料全部誤判成0筆）
- 根因：Supabase的REST API（PostgREST）單次請求預設最多回傳1000筆，超過的部分直接截斷，沒有任何警示
- 修法：任何一次性抓取「全部資料」的程式碼，只要資料量可能超過1000筆，一律要做`limit`+`offset`分頁抓取到抓不滿一頁為止；只需要「知道總筆數」不需要內容時，改用`Prefer: count=exact`搭配`Range: 0-0`拿筆數，不用真的把資料全部抓下來
- 一行規則：**碰Supabase的GET查詢，只要資料量有可能超過1000筆，預設就要做分頁**，不能假設「程式跑完沒報錯」就等於「資料抓齊了」——這個坑同一天在五個不同工具裡各自被踩到一次，值得列進遷移SQL的標準檢查清單

### 📅 2026-08-27：GAS的getSheetByName()偶爾對分頁名稱字串比對失敗，改用gid繞過
- 症狀：施工單管理搬遷腳本呼叫`getSheetByName('施工單查詢')`，在Apps Script編輯器手動執行時穩定失敗，丟出詭異的`Sheet 38985608 not found`（一串數字，明顯是別的試算表的gid，不是分頁名稱錯誤該有的訊息）；連原本沒被這次搬遷碰過的舊版`getOrders()`都遇到一樣的錯誤，但同一支程式碼透過真正的網頁請求（doPost）或排程觸發執行時完全正常
- 根因：懷疑跨系統複製貼上的分頁名稱字串（本機檔案→GitHub→剪貼簿→Google的編輯器）中間夾帶了看不見的特殊字元或不同的Unicode正規化形式，導致視覺上一樣的中文字在程式比對時判定不相等；且這個問題只在Apps Script IDE手動執行的情境下會發生，實際部署後的web請求/排程觸發不受影響
- 修法：改用分頁的內部代號（gid，不受文字差異影響）取代名稱字串比對，寫一個`診斷目前試算表()`小工具先列出`getSheets().map(s=>s.getSheetId())`確認實際gid再對應著用
- 一行規則：**跨系統複製貼上的中文字串不完全可信，尤其是拿來做程式比對用途時**——能用不受文字差異影響的ID/gid就優先用ID；遇到「程式碼看起來完全正確卻比對失敗」的詭異bug，先懷疑字元編碼差異，不要在程式邏輯裡鑽牛角尖

### 📅 2026-08-27：打烊/開店工具即時報表依賴，SQL遷移要多做「按需刷新快取」設計
- 症狀：打烊/開店的「進出資料表」原本評估直接搬Supabase當權威來源，但咖哩確認「打烊後」/預覽分頁是**晚班上班時即時核對用的公式報表**，直接依賴Sheets儲存格內容即時運算，風險比原本評估的更高
- 根因：搬去SQL之後，如果Sheets不再是即時寫入的權威來源，那些依賴Sheets儲存格公式的即時報表就會讀到過時資料，這是SQL遷移常見的「表面上是資料庫選擇，其實牽動了下游即時報表」的隱藏依賴
- 修法：把Sheets的「進出資料表」重新定位成「按需刷新的快取」——每次要切換預覽分頁或匯出前，都先呼叫一次刷新函式，把Supabase對應時段的最新資料清空重貼回Sheets，讓公式報表永遠讀到當下最新資料，而不是強行讓公式報表也改讀Supabase
- 一行規則：**SQL遷移前，除了確認「誰讀寫這份資料」，也要確認「有沒有下游功能依賴這份資料在Sheets裡的即時性」（例如公式報表、IMPORTRANGE）**——這種依賴不能簡單地全部丟給Supabase，可能需要「Supabase為主、Sheets按需同步回填」的混合設計

### 📅 2026-08-10：把 xlsx 重建成 HTML 表格列印，三個一定會踩的坑
- 症狀：同一份哨表，Excel 印出來正常，用 SheetJS 讀出來重建成 HTML 表格列印卻是：整張沒框線、表格縮在紙張左上角一小塊、比例跟 Excel 完全不像、最後還被切成 3 頁
- 根因：三件事各自獨立——①**框線要自己畫**：SheetJS 讀不出（也沒人幫你套）儲存格框線，td 不設 `border` 就是全白；②**沒處理合併儲存格**：`ws['!merges']` 不轉成 colspan/rowspan 的話，像「13人/12HR+8HR…」這種跨 6 欄的內容會被硬塞進單一窄欄，撐出又高又窄的格子把整張表撐爆；而且合併格的值**只存在左上角那格**，用「掃描有資料的最後一欄」找欄數會漏掉最後一欄（M4:N4 的值在 M4，N 欄是空的），實測欄數 13、應為 14；③**CSS 的 `height` 對表格列是「最小高度」語意**：Excel 的列高是絕對的、內容超出直接裁掉，CSS 則是內容需要多高就把列撐多高——標籤兩行的格子（`P3⏎車道`、`停巡7⏎(廣場哨)`）就把那幾列從 10.3mm 撐成 13.8mm，18 列累積多出 10mm 便超出紙張分頁
- 修法：框線比照原檔逐格套（第1列只有下框線）；`!merges` 轉 colspan/rowspan，被覆蓋的格子跳過不渲染，欄數要一併考慮 `!merges` 的最大欄。縮放比照抄 Excel 的 fitToPage：欄寬/列高/字級都保留原始「點」值放 `data-pt`，套 `scale = min(可用寬/原始寬, 可用高/原始高, 1)`；**上限 1 代表只縮不放**（內容少時 Excel 是留白而不是拉滿，少了這個 `1` 版面就完全不像）。因為列高會被內容撐開，scale 不能只算一次，要**套上去之後實際量測、超出再縮，迴圈到塞得下**；量測時暫時把容器撐成紙張寬（螢幕視窗比紙窄，不撐開會量到被壓縮的錯誤值），**量完一定要移除**——容器留著固定寬高，只要實際可列印區小一點點（印表機硬體邊界、捨入誤差）就會溢出、把表格切一半還多印一張
- 一行規則：**HTML 列印要模仿 Excel 版面時，框線、合併、縮放三件事都得自己做，而且縮放必須「算完再量、量完再縮」**——CSS 沒有 fitToPage，`height` 只保證最小不保證最大；另外分頁用的容器**永遠不要**設固定寬高，尺寸該由內容決定

- 修法：把整段 `<script>` 內容抽出來，用 `global.React = {createElement:()=>{}}`、`global.window = {...}`、`global.document = {getElementById:()=>null}` 等最小假物件把瀏覽器 API 都 stub 掉，再用 `new Function('module','exports','window','React',...,src)` 執行，最後從 `module.exports` 拿到純函式（前提是原始碼底部有 `try{ module.exports = {...} }catch(e){}` 這種防禦性寫法）
- 一行規則：單一 HTML 內嵌 React 的工具，只要底部有把核心邏輯函式掛到 `module.exports`，就能完全脫離瀏覽器用 node 跑單元測試，比每次等瀏覽器工具開起來快很多，這次哨表工具前後總共跑了快60項這類測試

### 📅 2026-07-14：時間複雜度(Big-O)參考表——動手寫迴圈/比對邏輯前先對照

> 這則不是踩坑事後補救，是**參考知識**：咖哩問到一支講「10種時間複雜度模式」的教學短片，記下來給以後寫程式前當對照，不用等真的卡頓了才回頭查。

- **核心觀念**：資料筆數（n）變多時，程式會變慢多少，用 `O(...)` 表示。天鷹保全 APP 目前員工/紀錄規模都是幾十到幾百筆，大部分寫法差異感覺不出來，但**規模一旦成長（例如TODO-27多案場版上線、員工數從20變200+）**，寫法差異會被放大到肉眼可見的卡頓。
- **從快到慢對照表**：

  | 模式 | 白話 | n變2倍會慢多少 | 天鷹APP裡的例子 |
  |---|---|---|---|
  | O(1) Hash Lookup | 直接查表拿答案 | 不變慢 | 用 empId 當 key 直接查員工資料 |
  | O(log n) Halving Loop | 每次砍半找 | 幾乎不變慢 | 二分搜尋（目前少用） |
  | O(n) Single Loop | 每筆看一次 | 慢2倍 | 逐月掃描班表、逐筆算工時 |
  | O(n+m) Sequential Loops | 兩個獨立迴圈各跑一次 | 慢2倍 | 分別掃「進」「出」兩張表再合併 |
  | O(n log n) | 迴圈裡包一次砍半搜尋 | 慢略多於2倍 | 排序後逐筆比對 |
  | **O(n²) Nested Loop** ⚠️ | 每筆對每筆比（迴圈包迴圈） | **慢4倍** | **每個員工都要跟每個員工比對一次**（例如查重複打卡、算所有人互相衝堂）——**這是最容易不小心寫出來、也最容易拖垮效能的寫法** |
  | O(2ⁿ) / O(n!) | 遞迴分裂/列所有排列組合 | 爆炸性變慢 | 天鷹目前沒有真實需求會用到，出現在程式碼裡通常是寫錯方向 |

- **一行規則**：**寫任何「兩份清單互相比對」或「每筆資料都要跟其他所有筆比一次」的邏輯前，先想有沒有辦法用「查表(Map/物件當索引)」取代「巢狀迴圈逐筆比對」**——前者是 O(n)，後者是 O(n²)，資料量一大差異會很明顯。改動涉及大量資料處理（哨表自動化 TODO-12、多案場版 TODO-27）時，交付前主動問一句「這段邏輯是不是巢狀迴圈，資料量大了會不會變慢」。

### 📅 2026-07-13：咖哩海域跑步動畫批次擴充（brain_map.html RUN_IMG_MAP）——去背演算法/來源圖不一致/自己手殘刪檔三個坑

> 咖哩上傳12支角色的「12格跑步姿勢格狀圖」到 `brain_map_img/run_<英文名>.png`（艾斯/布魯克/喬巴/克比/弗蘭奇/甚平/羅/娜美/佩羅娜/山治/烏索普/索隆），要求比照既有路飛/羅賓的跑步循環機制補完。最後只完成6隻（索隆/娜美/喬巴/山治/烏索普/羅），另6隻卡在來源圖品質，記錄如下供下次接手判斷。

- **去背演算法：`cv2.floodFill` 預設「浮動比較」會沿陰影漸層走到角色身上，必須加 `FLOODFILL_FIXED_RANGE`**：第一版直接對純黑背景做 flood fill 去背，Zoro深綠色袍子的陰影摺痕大片被誤判成背景整片消失。原因是 floodFill 預設用「跟鄰居像素比」而非「跟原始種子色比」，遇到背景純黑→陰影深綠色的漸層會一路吃進角色內部。**改法**：`flags` 加上 `cv2.FLOODFILL_FIXED_RANGE`，強制只跟純黑種子值(0,0,0)比對(±22容差)，不管鄰居像素，之後索隆的深色陰影就正確保留。純黑背景+近黑色服裝（如山治全黑西裝）去背後該處alpha會是0（技術上「摳空」），但因為APP場景背景本身是深色(#0A0C10)，實際疊圖後完全看不出來，等於瑕疵剛好被深色主題蓋掉——**判斷去背品質不能只看PNG本身在白底/棋盤格底下的樣子，要疊到實際部署背景色上再看**，這次差點誤判「山治壞掉了」。

### 📅 2026-07-13：今/明日哨表晚班區重複人員 — 兩個獨立根因（PR #125~128）

- **症狀**：APP 今/明日哨表畫面晚班區同一人重複出現、哨位標籤對不上本人真實排班（如陳國榮早班明明是「警衛室」，晚班卻多出「帶隊幹部」「漢來飯店」兩筆），另有大量「未標示」。
- **根因① `fillMergedCells_` 呼叫了不存在的 API**：`sh.getMergedRanges()` 是 `Range` 的方法不是 `Sheet` 的，從第一天起每次呼叫都丟 `TypeError`，但外層包了 `try{}catch(e){}` 靜默吞掉——這個「把合併儲存格的值展開複製到整個範圍」的函式從沒真正執行過。後果：合併儲存格只有左上角那格讀得到值，其餘格子在 `values` 裡其實是空字串，往回找哨位標籤時常常撲空（→未標示）或跨欄撞到不相干的文字。**改法**：`sh.getDataRange().getMergedRanges()`。
- **根因② 表格外還有一份不相干的獨立名單，被整批誤判成晚班資料**：試算表在早/晚班完整表格（A~N欄）結束後，還有 P 欄（甚至到 Q~W）放著使用者自己在來源 Excel 做下拉選單用的輔助清單，**沒有自己的哨位標籤，也不在任何早/晚班表頭合併範圍內**。程式原本掃描每一欄，只要欄位數字比晚班區晚，就無條件當晚班資料處理，往回找標籤時撞到最近的文字就硬貼——這才是陳國榮那兩筆「重複」的真正來源，跟他本人的班表完全無關。**改法**：①讀取端（`parsePostFullList_`/`parsePostSheet_`）改成「逐欄看表頭寫早班還是晚班」（`buildColBlockMap_`），不在任何表頭範圍內的欄位直接跳過不猜測 ②上傳端（`哨表上傳_GAS_v6.gs`）改成只寫入 A~N 欄（`GUARD_MAX_COLS=14`），輔助欄位從源頭就不寫進正式試算表。
- **除錯關鍵**：手機截圖只能看到「症狀」，看不到「哪一格資料造成的」——這次靠加一個 `診斷哨表原始格內容()` 直接 dump 原始儲存格＋合併範圍到 Log，加上使用者後來直接提供來源 Excel（用 Python 直接解 xlsx 內部 XML，不需要 openpyxl/xlsx 套件），才真正定位到兩個根因。純靠猜欄位編號來回試了三輪都沒中，**遇到「表格解析結果對不上畫面」這類問題，直接要原始資料或加 dump 工具，比對著截圖肉眼數欄位快得多、也準得多**。
- **一行規則**：GAS 裡看到 `sh.getMergedRanges()`（呼叫在 Sheet 物件上）一律是 bug，正確寫法是 `sh.getDataRange().getMergedRanges()`（Range 的方法）；解析「表格式試算表」時，任何超出表頭合併範圍的欄位都要明確排除，不能用「欄位數字比較」當班別判斷依據。

### 📅 2026-07-11：互動吉祥物系統 — LINE 貼圖去背/多段接力動畫/瘦身全流程

> 首頁新增可拖曳換裝的吉祥物（`MascotWidget`，見 `brain_map.html` 節點136），角色素材大多來自咖哩傳的 LINE 貼圖小舖螢幕錄影，AI 自己截幀去背做成透明動態 webp。這篇記完整流程與踩過的坑，之後再加角色直接照此複製。

- **判斷「這支影片能不能用」先看背景，不是看角色**：LINE 貼圖有兩種截法——①聊天室裡的靜態貼圖訊息（逐幀比對 pixel diff 幾乎是0，代表真的是靜態圖，用不出動畫）②貼圖小舖裡「點開貼圖」的官方預覽（enlarge 動畫，這才是真的在動）。用 `numpy` 算連續幀的 `mean(abs(diff))`，趨近0＝靜態，有周期性起伏＝真動畫，抓最低點所在的 period 就是循環長度（通常 30fps 抓下來 period 落在 20~30 幀，約0.7~1秒一輪）。
- **去背核心演算法：「填滿封閉輪廓」不能用 `findContours`+`drawContours(FILLED)`，要用「外部 flood-fill 反推」**：
  - 錯誤做法：對線稿的外框做 `RETR_EXTERNAL` 找最大 contour 再填滿——**這在描邊很細/複雜（毛絨蓬鬆輪廓、多處窄橋接）時會隨機失敗**，某些幀只填出一圈細線（内部沒填滿），肉眼看起來是「鏤空」或整隻變單色色塊，且會隨幀變化（同一支動畫有的幀正常有的幀壞掉），因為 contour 追蹤在細線處會把「內部」跟「外部」搞混。
  - 正確做法：①用飽和度/明暗門檻抓出線稿的黑色描邊 mask（不是整個角色，只抓描邊）②`dilate`+`morphologyEx(MORPH_CLOSE, 大kernel如9x9, 2 iterations)` 把描邊的細小缺口橋接起來，橋接前先把畫布四邊各清空2px確保「外部」一定連通③從畫布角落 `floodFill` 往內灌，凡是灌得到的都是「外部」④「非外部 且 非描邊」的區域＝封閉的內部，直接判定為前景，不管內部原本是什麼顏色（白肚子、黑眼睛都一視同仁收進來）。這個方法對任何線稿封閉圖形都穩定，改了才把之前間歇性失敗的角色（瞌睡羊/奔騰小馬毛絨輪廓）全部修好。
  - **例外**：如果角色原始美術稿本身底部就沒封閉（貼圖故意裁到聊天泡泡下緣），這個方法會誠實地把那塊判成「不是內部」變透明——這不是 bug，是美術稿本身沒畫全，遇到就承認是小瑕疵記錄下來（咖波第一版肚子、白爛貓「髒東西」頭部缺角都是這個原因），不用硬修。
- **旁邊貼圖殘影／大字說明文字要手動排除**：LINE 貼圖小舖預覽時，畫面常帶：①旁邊被半透明蓋住的鄰居貼圖（淡灰色殘影）②貼圖名稱大字（如「轉帳中」「急速前進!!」）。殘影通常靠飽和度門檻就會自然濾掉（因為夠淡），但大字說明文字是黑色高對比，跟角色描邊同等級，**一定會被一起抓進前景**，必須額外開 `exclude_rect`（可傳多個矩形）在做飽和度門檻**之前**先把那塊區域清成背景色。矩形座標每支影片都要重新拿 ruler 疊圖手動量，沒有通用公式。
- **背景裝飾（雨滴線條/速度線）跟角色離太近會被形態學閉運算橋接成同一坨**：「晴天霹靂」那支鯊魚貼圖背景有滿版黃色雨滴裝飾線，因為離角色輪廓很近，`MORPH_CLOSE` 用大 kernel 橋接毛絨缺口時，順便把雨滴線也橋接進同一個連通分量，導致「保留最大2個連通分量」這招失效（雨滴+角色變成同一個最大分量）。目前沒有通用解法，只能靠縮小該支影片專用的 closing kernel（3x3 而非 9x9）試，試了還是不乾淨就先跳過那個場景，不要死磕——這次是直接放棄鯊魚先生的第4段動畫，只做3段接力。
- **多段動畫接力循環＝直接把多支 webp 的幀陣列串在一起存成一支 webp**：不用寫任何播放控制邏輯。`PIL.Image.open(...).seek(i)` 把每支已完成的 webp 幀讀出來，四段依序 A+B+C+D 串成一個 list，用**最大寬高**建立統一畫布、每幀**底部置中對齊**貼上去（貼圖角色常常整隻高矮不一，底部對齊比正中對齊更不會有場景切換時「飄移」的違和感），`save_all=True, loop=0` 存檔即可，瀏覽器 `<img>` 標籤原生支援 A→B→C→D→A 無限循環播放，前端 `MascotWidget` 元件完全不用改一行程式碼（角色資料只是換一個 `img` 路徑指到新檔案）。
- **素材瘦身規格（顯示尺寸只有64~96px，來源不需要原始解析度）**：擷取直接用 `fps=15`（不要fps=30再事後砍半，一次到位）、每幀縮到 **240px 上限**（`Image.LANCZOS`）、`quality=78`（原本用90+，肉眼在實際顯示尺寸下比對不出差異）。6支角色動畫實測從 2713KB 瘦身到 981KB（-64%），之後新角色一律套這組參數，不用等咖哩發現變重再回頭瘦身。
- **版權判斷標準（已跟咖哩對過三次，以此為準）**：個人/小型創作者的 LINE 貼圖（咖波、白爛貓這種）風險等級可接受，直接做；**大型商業公司官方 IP（航海王付費動態貼圖包有 Toei/Shueisha/Oda 版權標示、皮卡丘、三麗鷗布丁狗/蛋黃哥）一律婉拒**，不管是要「抓影片幀」還是「拿單張官方插畫做假動畫」，換個技術手法不會讓版權問題消失——**這條線不會因為對方說「可以改一下嗎」而鬆動**。

### 📅 2026-07-03：GitHub Pages 部署卡死佇列 — 取消失敗的正確應對

- **症狀**：GitHub Pages 部署（`pages build and deployment`）累積 **9 筆卡在 `queued`**，最舊一筆卡了超過 12 小時；網頁上的 Cancel 按鈕、API 呼叫全部失敗。
- **根因**：GitHub 平台端問題（runner 沒被分配到這批 run），**不是 repo 或程式碼壞掉**。可先查 [githubstatus.com](https://www.githubstatus.com/) 確認有無事故公告。
- **關鍵發現：卡住的 queued run 無法取消**。呼叫 cancel API 一律回 `409 Cannot cancel a workflow re-run that has not yet queued.`，網頁按鈕也是同一個內部錯誤，**不用再重試**。
- **正確做法（不是取消，是蓋過去）**：
  1. GitHub Pages 只認**最新一次成功部署**，不需要把佇列裡的殭屍逐筆清掉。
  2. 直接推一個新 commit（哪怕是空 commit：`git commit-tree <tree> -p <parent> -m "..."`）觸發全新的部署 run。

  4. 舊的殭屍 `queued` run 放著不用管，GitHub 會在逾時（最長 72 小時）後自動標記失敗並清掉，不影響網站也不影響新部署。
- **教訓**：遇到「取消/刪除卡住的雲端資源」一直失敗時，先想「有沒有辦法繞過去（用新資源蓋過舊的）」，不要在明知會 409 的操作上重試消耗時間。

### 📅 2026-06-27：開店前工具 + 多工具修正

#### A. 工具嵌入有兩種模式（決定新工具怎麼放）
1. **base64 內嵌**：`<script id="tpl-X" type="application/octet-stream">…</script>`，用 `b64decode()` → iframe `srcDoc`（closing/car/signin/emergency/upload）。
2. **獨立檔 + iframe `src`**：獨立 HTML 放 repo 根，常數存 GitHub Pages URL（`POST_PAGE_URL`、`OPENING_PAGE_URL`），render 用 `src` 不用 `srcDoc`（post.html / tool_opening.html）。
- **決策準則**：要獨立維護、檔案分離、好單獨預覽 → 選獨立檔模式。要單檔打包 → 選 base64。
- **改 base64 內嵌工具 SOP**：Python regex 抓 `<script id="tpl-X"[^>]*>(.*?)</script>` → `base64.b64decode` → 編輯字串 → `base64.b64encode` → 取代回 index.html。改完一定 `node --check`。

#### B. GAS `getActiveSpreadsheet()` 只能讀寫綁定的那份試算表
- 跨試算表共用資料時必須**多個 GAS URL**。開店工具範例：`DB_GAS_URL`（打烊 GAS，共用 `_SharedDB` 廠商/監工/檢查者）+ `BUILT_IN_GAS_URL`（開店 GAS，寫各自記錄）。
- 想單一 GAS 跨表寫入要改用 `openById()`，且 GAS 帳號需有目標表存取權。

#### C. 常見錯誤 → 修法
| 症狀 | 根因 | 修法 |
|------|------|------|
| 送出失敗「找不到分頁」 | 前端 `BUILT_IN_SHEET` 與實際分頁名不符 | 對齊實際分頁名；GAS `getSheetByName` 區分大小寫/全形 |
| 「今日」讀不到剛送的資料 | 繼承的 `getTodayRows` 用夜班時段(20:00~隔日00:00)，早班資料落窗外 | 改日曆日(今天00:00~隔日00:00)；**GAS 改了要重新部署**（管理部署→編輯→新版本，網址不變） |
| 手機/工號開頭 0 消失 | Google Sheet 把純數字字串當 number 存，回傳掉前導 0 | 前端 `normalizePhone()` 補回；或試算表欄位設「純文字」格式；或 GAS 寫入時加 `'` 前綴 |
| 班別/代號不顯示、編輯選不到 | 代號未在 `SHIFT_TYPES` 定義（render 成「·」，編輯視窗 iterate `SHIFT_TYPES`） | 補定義（代號/label/time/color/bg/hours）+ 同步 `WORK_SHIFT`/`OFF_TYPES` |

#### D. 權限控制（工具內角色判定）
- 工具讀 `localStorage.hsh_session_user` 的 `role`。限管理員：`['admin'].includes(u.role)`。
- `window.self===window.top` 旁路：獨立開啟（部署設定/githack 預覽）時放行；App 內嵌 iframe 則依角色。

#### E. 分支預覽方法
- 用 **raw.githack.com + commit SHA**（不要用分支名——分支名含斜線 `claude/...` 會造成路徑歧義）：
  `https://raw.githack.com/<user>/<repo>/<full-SHA>/<path>`
- base64 內嵌工具無法單獨預覽 → 解碼成獨立檔暫放 `preview/`，合併前刪。
- Google Sheets 嵌入 `/preview?gid=X` 可切分頁；手機底部分頁列易被擠掉 → 自製按鈕改 iframe `src` 的 gid。

#### F. 合併 main：base64 內嵌工具的衝突處理
- base64 是「一行超長字串」→ git 視為單行衝突，**無法逐行 merge**。
- 處理流程：解碼衝突雙方（HEAD vs 分支）→ `diff` 找真實差異 → 確認某方是 superset → 取較完整版重貼。
- **教訓**：base64 內嵌讓 git diff/merge 失效，是內嵌模式最大缺點；高頻修改的工具建議改獨立檔。

#### G. 驗證手法
- HTML 內嵌 JS 驗證：Python 抽出 `<script>`（排除 `src=` 與 `octet-stream` 模板）合併 → `node --check`。
- GAS 在 template literal 內：抽出 `const GAS_CODE=\`…\`` → 存 `.js` → `node --check`（`.gs` 副檔名 node 不認）。
- 主鍵規範：純數字流水號 `nextRow-1`，**禁止** `genId()` 隨機英數。

## 2026-08-19：GAS 寫入函式「一邊驗一邊寫」＝驗證失敗也會留下壞資料

做無線電管理工具（TODO-25）時，用假的 `SpreadsheetApp` 把後端整套寫入流程跑一遍，
抓到兩個自己讀程式讀不出來的 bug，兩個是同一種型：**驗證夾在 setValue 中間**。

`setStatus_` 原本長這樣：

```javascript
sh.getRange(o.row, 8).setValue(status);      // ← 先寫
if (status !== '使用中') { ...清空使用者... }
else if (!o.userName) {
  return jsonRes_({ status: 'error', msg: '要改成「使用中」請用撥發功能指定使用者' });
}
```

前端收到 error、跳紅色 toast、使用者以為沒改到，但試算表那一列已經是
「狀態＝使用中、使用者＝空白」。這正好違反這個工具最重要的不變式
（非使用中就一定沒人／使用中就一定有人），統計台數從此對不起來，
而且沒有任何人會發現——因為畫面明明說失敗了。

`updateRadio_` 是同一件事的另一個版本：機型、日期、案場一欄一欄寫下去，
寫到一半才驗「歸屬」，歸屬打錯就中途 return，前面幾欄已經進去了，
變成「改了一半」。

**教訓**：GAS 的 sheet 寫入沒有交易可回滾，一個 return 就地中止，
前面寫過的全部留著。所以**所有驗證必須在第一個 setValue 之前全部做完**，
驗證區與寫入區分開兩段，中間不要交錯。

**這種 bug 只有跑得起來才抓得到**。純看程式碼很難察覺，因為每一行單獨看都對；
code review 也容易略過（順序問題不像邏輯錯誤那麼刺眼）。做法是把
`SpreadsheetApp`／`UrlFetchApp`／`Utilities` 用 30 行假物件頂替，
`eval` 整份 .gs 進去，然後直接呼叫 `doPost`／`doGet`，
最後對「全表跑一次不變式」下斷言：

```javascript
ok('全表：非使用中一律沒有使用者', radios().every(r => r.status === '使用中' || !r.userName));
ok('全表：使用中一律有使用者',   radios().every(r => r.status !== '使用中' || !!r.userName));
```

單筆斷言只會驗到你想得到的路徑，**全表不變式會把你沒想到的路徑一起抓出來**——
上面那個 bug 就是被第二條抓到的，不是被「改使用中應該回錯誤」那條。
